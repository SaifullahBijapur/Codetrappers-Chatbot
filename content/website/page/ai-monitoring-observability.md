    What was asked, which tools ran with which arguments, what came back, and how long each step took. Without that, debugging an AI system is guesswork dressed up as intuition.

2.  ### Treat cost as a first-class number

    Tokens and spend per run, per feature and per customer, watched on the same dashboard as errors. AI bills do not creep, they step, and the step is usually a prompt change nobody flagged.

3.  ### Record what was retrieved, not only what was said

    When an answer is wrong, the useful question is almost always which passages the system pulled. Logging the retrieval alongside the response turns a complaint into a fixable bug.

4.  ### Catch the quiet failures

    Refusal rates climbing, retries increasing, latency drifting, a tool silently returning empty since a supplier changed a field. None of these page anybody. All of them are visible in the numbers before anyone notices.

5.  ### Prove it still works after every change

    A set of tasks with known good outcomes, run on every prompt edit, model upgrade and deployment. Without one, every improvement is anecdotal and every regression is a surprise.

## What observability will not do

Three things worth being clear about before anyone buys a dashboard.

### It does not stop hallucination

It shows you where and how often it happens, which is what lets you fix the retrieval or the prompt that caused it. Anyone selling monitoring as a cure for wrong answers is selling you a thermometer as a treatment.

### Logs are personal data

Traces of real conversations contain whatever your users typed. Retention periods, redaction and access control are part of the build, not a later concern, and they are the reason this work sits next to governance rather than apart from it.

### A dashboard nobody opens is not observability

The measure is whether the right person hears about the right problem without going to look. That means alerting on a small number of things people will act on, rather than forty charts that make an impressive screenshot.
