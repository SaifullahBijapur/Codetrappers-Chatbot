1.  ### Start from the job, not the model

    Most requests we get are really a scheduled query nobody has time to run. That part is cheaper, faster and more reliable built without a model, and we will say so before quoting.

2.  ### Give it tools rather than instructions

    An agent told what to do in a prompt will improvise. An agent given a fixed set of described tools, each with a schema and a permission check, can only do the things you built.

3.  ### Bound the blast radius before the first run

    What it can read, what it can change, how much it can spend and how many times it can loop. Decided up front, enforced in code, not left to good behaviour.

4.  ### Keep a person on anything irreversible

    Sending, publishing, charging, deleting. Those get drafted and queued, because the cost of being wrong is not symmetrical and never has been.

5.  ### Watch it after launch, because it will drift

    Inputs change, a supplier renames a field, a model version updates. An agent that quietly started failing three weeks ago is the normal failure mode, not a dramatic one.

## What we build

### Operations agents

The morning sweep: stuck orders, failed payments, stalled tickets, stock that has been out for a month. Read-only to begin with, which is where most of the value is anyway.

### Support triage agents

Match an inbound message to the order, the shipment and the product, summarise the history, and draft a reply for a person to send.

### Content and catalogue agents

Bulk work with judgement in it, such as writing descriptions from real product data and flagging the records where the data is too thin to describe honestly.

### Reporting agents

Questions answered from live data rather than a dashboard nobody opens, delivered where your team already works.

### Monitoring and maintenance

A retainer covering tool call volume, failure and refusal rates, cost per run, and the regression tests that catch drift before a client does.

### An evaluation harness

A set of tasks with known good outcomes, run on every change. Without one, every improvement is anecdotal and every regression is a surprise.

## Where agent projects go wrong

Three failures account for most of the disappointment, and none of them are about model quality.

### Too much permission, too early

Write access granted on day one produces an agent nobody trusts enough to leave running. Read-only first earns the confidence to grant more later.

### No log anyone can read

When something odd surfaces a month later, the only useful question is which tool ran with which arguments. That cannot be answered retrospectively.

### Tool output treated as instruction

Text that comes back from a web page, a ticket or a document is data, not a command. An agent that does not draw that line can be steered by anyone who can write into one of those systems.
