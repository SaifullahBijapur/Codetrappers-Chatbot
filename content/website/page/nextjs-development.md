## Where a Next.js front-end earns its place

Not every site needs one. These are the cases where it does.

### Content sites that outgrew the theme

Editors keep their CMS, visitors get a front-end that renders in milliseconds and does not break when a plugin updates.

### Commerce storefronts

Custom storefronts on Shopify, WooCommerce or a commerce API, with the checkout you want rather than the one the theme allows.

### Web applications

Dashboards, portals and internal tools with authentication, real-time data and the interaction quality people expect from software.

### Multi-brand and multi-region

One codebase, many sites: shared components, per-brand themes, per-region content and a single deploy pipeline.

### Marketing sites with a design budget

When the design is the product, a component-driven front-end reproduces it exactly instead of approximating it in a page builder.

### Gradual migration

Route by route, the new front-end takes over from the old site behind the same domain, so nothing has to launch all at once.

## Common pairings

### Headless WordPress

Editors keep the WordPress admin, the front-end is Next.js. Our most common architecture, and it has its own page.

### Serverless and edge

Rendering at the edge with Cloudflare Workers or Vercel Edge, for global audiences and spiky traffic.

### Mobile apps from the same code

Shared components and API layer with a React Native or Capacitor app, so one team ships both.
